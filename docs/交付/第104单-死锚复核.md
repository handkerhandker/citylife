# 第 104 单 · 死锚复核：给"便利店·货架"一个用途，量下来不划算（**已评估、退回**）

> 一句话：`store_shelf`（便利店·货架）从第 12 单放样起**全代码零引用**（第 19 单登记：30 天双种子到访 0 人次）。
> 本单试给它一个真实用途——**店员上班时段去理货**（11 点档／16 点档各一程）：功能本身成立
> （她站货架 **392–399 拍/30 天**、理货日志 **50–51 条/30 天**），但它把**世界纹理拧歪**了：
> 她多走两趟（柜台↔货架）⇒ 每程多 10 分钟路程 ⇒ 班次节律漂、别人的日子跟着变 ——
> 门禁当场拒收：第 64 单那条"生日上卡 ≥16"掉到 **13/24**。照"**不搞出新 bug 为最高准则**"，
> **退回**：`city-life-framework.html` 回到 v95 的状态，产品代码零改动 ⇒ **不涨号**（仍 v95）。
> 保留的是**评估结论**与工具能力（`rel-audit --忽略=<字段>`）。

## 一 · 试了什么

```js
// （已退回的写法，留档）店员上班时段里 11 点档／16 点档各去货架一程：
const 理货=(ag.workKind==='clerk') && ((mod>=11*60&&mod<12*60) || (mod>=16*60&&mod<17*60));
setActivity(w,ag,'store_shelf','work','理货',60,thought, logText!==null?logText:'在货架上理了理货');
```

两处细节都是踩出来的：① 判据**不能用"整点那一拍"**——工作块 60 分钟一程、起步点随走路漂
（实测 10:20／11:20…），"正好 11:00"那拍她多半正忙、整段错过；改成"这一程起步落在 11 点档"才对上。
② 一开始把理货那句归进 `work` 类，结果"丙级·上班频次"多出两条/天 ⇒ 频次项变响、当天卡更容易被频次抢走。

## 二 · 读数：功能成立，但代价在别处

| 读数 | 结果 |
|---|---|
| 她站在货架上的拍数（30 天） | **392–399 拍**（约 65 小时）——死锚**真的被用起来了** |
| 理货日志（30 天） | **50–51 条**（约 1.7/天；她午休／休班时那两档自然缺席） |
| 跨版本逐拍比对（`rel-audit --before=HEAD`） | **第 49 拍就分叉**：`store_counter` → `store_shelf`（预期），**但 `busyUntil` 也跟着差 10 分钟** |
| 三种补差写法 | ①写死 50 分钟 ⇒ 第 18 拍分叉；②按"是否要走路"补 ⇒ 第 887 拍分叉；③只补"多出来的那段" ⇒ 仍会从**吃饭／午饭**那几支多走回来 ✗ 补不干净 |
| **第 64 单闸**（生日上卡 ≥16，6 种子 × 4 人） | **13/24** ⇒ **判红** |
| 第 88 单闸（两天里每对每天至多 +1） | 也报出越界（她的节律一变，别人的聊天日跟着变） |

**结论**：位置变了，"哪一程要走路"这件事本身就跟着变——补不回来。而它带来的收益只是**一个观感**
（店里有个人在货架那儿理货），代价却是**世界纹理的变化**（生日上卡这种旗舰读数的覆盖率掉下来了）。
按最高准则（不搞出新 bug）——**退回**。
