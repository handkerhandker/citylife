## 0. 一句话结论

病根**不在寻路、不在平滑器的豁免分支**，而在**一句判据的位置**：
显示坐标的推进（`stepDisplay`）长在 `draw()` 里，而 `draw()` 挂在 `#scr-live.active` 下；
`updateWalkers` 与 `Sim.step` 却在 `loop()` 里无条件跑。
**切页 ⇒ 真实位照走、显示位冻结**，两者最大拉开 36.35 格（横跨整张 47×28 的地图）；
切回时平滑器把这段积压当成一次普通追赶，**按直线、以 (5.5×速度+6) 格/秒 一路划过去**——
不寻路、不绕障碍、穿墙穿家具。

治法是**把显示推进从 `draw()` 提到 `loop()`**，紧跟 `updateWalkers` 之后无条件执行。
不是「切回时补一次直置」，而是**让显示位压根没有机会落后**：每帧 `|真实位 − 显示位| ≡ 0`。
故切回时人本来就在该在的地方，无跳变、无补间、无假动画，
且**不新增任何直置通道**——`v.warp` 的两处白名单逐字未动。

## 1. 取证四问

### 问一 · 切页时渲染循环与显示坐标更新究竟停在哪一步？

逐处列出主循环 `loop()`（`city-life-framework.html:3221–3248`，治前行号）的每一步，标注切页时是否照跑：

| # | 步骤 | 切到「日志」页后 | 依据 |
|---|---|---|---|
| 1 | `dtFrame=Math.min(0.1,(now-state.lastTs)/1000)` | **照跑** | `loop()` 由 rAF 无条件驱动 |
| 2 | `Input.pollPad(now)` | **照跑** | 同上 |
| 3 | `Sim.step(w, chunk)`（世界推进） | **照跑** | 只受 `w.speed>0` 约束，与页面无关 |
| 4 | `updateWalkers(dtFrame)`（**真实位 `v.x/v.y` 沿寻路折线前进**） | **照跑** | `loop()` 内无条件调用 |
| 5 | `updateCamera(dtFrame)` | **照跑** | 同上 |
| 6 | `drainLog()` / 每拍的各页重渲染 | 照跑（按页分支） | — |
| 7 | `draw(now)` | **停** | `if($('#scr-live').classList.contains('active')) draw(now);` |
| 8 | └ `stepDisplay(ag,dtFrame,pixOn)`（**显示位 `v.dspX/v.dspY` 推进**） | **停** | 全渲染层唯一调用点在 `draw()` 内（`:3112`） |

**停摆点精确到一处**：第 8 步。`stepDisplay` 在治前的全渲染层**只有一个调用点**，
就在 `draw()` 的住户循环里；`draw()` 一被判据关掉，显示位推进随之整个停摆。
第 3、4 步却一步没停 —— **这就是落差的来源**。

> 附注：`stepDisplay` 只有一个调用点这件事本身是第 20 单「规矩三·显示位置只有一个来源」的成果，
> 是对的。错的是这唯一的调用点被放在了一个**有条件执行**的函数里。

### 问二 · 切回时显示坐标是怎么追上真实位置的？走的是哪条代码路径？

走的是 `stepDisplay` 的**限速追赶支**，逐行如下（治前 `:3007–3020`）：

```js
function stepDisplay(ag,dtSec,pixOn){
  const v=state.vis[ag.id];
  let tx=v.x, ty=v.y;                                   // ← 目标＝真实位（切页期间已跑远）
  if(usePix && !v.moving){ …pixStandPos… }              // 兜底钳制：走线保证脚底非实体格，恒为空操作
  if(v.dspX===undefined || v.warp){ … }                 // ← 直置支：**本病症全程没有走这里**
  else{
    const dx=tx-v.dspX, dy=ty-v.dspY, len=Math.hypot(dx,dy);
    const cap=(5.5*(state.world.speed||1)+6)*dtSec;     // 1×＝11.5 格/秒，2×＝17 格/秒
    if(len<=cap){ v.dspX=tx; v.dspY=ty; }
    else{ v.dspX+=dx/len*cap; v.dspY+=dy/len*cap; }     // ← **这一行就是那根直线**
  }
}
```

三问三答：

- **是否经过寻路？** **否。** `dx/len, dy/len` 是从当前显示位指向真实位的**单位向量**，
  与 `v.path`（寻路折线）毫无关系。折线只被 `updateWalkers` 用来推进 `v.x/v.y`，
  显示位这一支从不读它。
- **是否经过平滑器？** **是，而且正是平滑器本身干的。** 但它不是「补一帧」，
  而是**以 cap 为速率、连续若干帧地划过去**：实测 1× 下持续 185–337 人帧（≈3–5.6 秒），
  这正是决策者看到的「飞」——不是一闪，是**看得见的一段直线飞行**。
- **是否走了豁免分支？** **否。** `v.warp` 在整个切页-返回过程中**从未置位**
  （门禁实测：病态写法下「白名单外直置 0 次」）。
  参谋假说「归进了场景切换/恢复渲染的豁免分支」**据此证伪**——见问三。

### 问三 · 铁律一为什么没拦住？（逐字归因）

**结论：不是落进了哪个豁免，而是压根没被采样到。**

逐字对照 `walkgate.js` 治前的判据（`:133` 与 `:146`）：

```js
const cap=WALK*speed*dt*STEP_SLACK;          // 5.5 × 速度 × dt × 1.05
ok(q.r.maxStep<=q.cap, …);                   // 判据本身
```

而 `maxStep` 的采样来自 `sample()`（`:70–101`）：

```js
for(let f=0;f<nFrames;f++){
  …Sim.step…
  V.updateWalkers(dt);
  for(const ag of w.agents){
    …
    V.stepDisplay(ag,dt,true);               // ← **每一帧都调，无条件**
    …
  }
}
```

**病根就在这一行的「无条件」**：`sample()` 复演主循环时，把 `stepDisplay` 直接写在了
`updateWalkers` 后面，等于**默认「显示推进从不停摆」**。生产代码里它却挂在 `draw()` 下。
于是门禁复演的是一个**根本不存在切页的世界**，那道缝自然一次也没被踩到。

三条逐字核对：

| 逐字对照项 | 结论 |
|---|---|
| 判据式 `d ≤ 5.5×speed×dt×1.05` 本身有没有错？ | **没错。** |
| 这一下是落在了 `warped` 豁免里吗？ | **不是。** `warped=(v.dspX===undefined)||!!v.warp`，两者全程为假；本病症走的是 `else` 支，会被正常计入 `maxStep`。 |
| 那为什么 `maxStep` 没超？ | **因为这些帧从来没被生成过。** 采样循环里不存在「跳过 stepDisplay 若干帧」的情形。 |

**假如采样到了，铁律一会不会报？——会，而且报得很响。** 实测：

| 速度 | 追赶速率 cap = (5.5×speed+6)×dt | 铁律一阈值 = 5.5×speed×dt×1.05 | 比值 |
|---|---|---|---|
| 1× | 11.5×dt ＝ **0.19167 格/帧** | 5.775×dt ＝ 0.09625 格/帧 | **1.99 倍** |
| 2× | 17×dt ＝ **0.28333 格/帧** | 11.55×dt ＝ 0.19250 格/帧 | **1.47 倍** |

也就是说：**平滑器的追赶速率天生就比铁律一的上限快 1.5–2 倍**
（`+6` 那一项是第 20 单为「保证追随不落后」留的过渡余量）。
在正常运行下这道差从不显形——因为 `cap` 恒大于 `updateWalkers` 的单帧步长，
限速器从来不是瓶颈，`len<=cap` 恒成立、走的是精确赋值那一支
（治前 `walkgate.js` 自己就打印着「限速器从未成为瓶颈」）。
**只有攒出积压时它才第一次真正生效，而一生效就直接越过铁律一的线。**

> **与第 20 单那道缝的同异**：第 20 单是「位移超过 3 格就当传送直接放过」——
> **判据错**（按距离猜意图）。本单是**判据对、采样范围不对**。
> 两者的共同祖先是同一个思维习惯：**只验「正常路径」，不验「被打断的路径」。**

### 问四 · 除了切页，还有哪些情形会让渲染停摆而 SIM 继续？——普查表

**判别法（本单立）**：会不会飞，只取决于一件事——
**「真实位推进」与「显示位推进」这两步，是不是被同一个开关控制。**
同停同走则永不飞；一个停一个走就必飞。

| # | 情形 | 停摆的是什么 | 真实位推进 | 显示位推进（治前） | **治前会不会飞** | **治后** |
|---|---|---|---|---|---|---|
| ① | **切页**（现场 ↔ 日志/角色/剪辑/手机/设置） | 只有 `draw()` | **跑** | **停** | **会飞** ← 本单病症 | 不飞 |
| ② | 浏览器标签页切走 / 最小化 | 整条 rAF | 停 | 停 | 不飞 | 不飞 |
| ③ | 窗口失焦（rAF 被节流到低帧率） | 无（只是 dt 变大） | 跑（大 dt） | 跑（同一个大 dt） | 不飞 | 不飞 |
| ④ | 存档载入 | 整页 `location.reload()` | 重新 boot | 重新 boot（首帧 warp） | 不飞 | 不飞 |
| ⑤ | 暂停后恢复（`w.speed=0`） | `Sim.step` 与 `updateWalkers` 双双冻结 | 停 | 跑（追上后即静止） | 不飞 | 不飞 |
| ⑥ | reduceMotion 开 | 无 | 跑 | 跑（锚变时走直置豁免） | 不飞 | 不飞 |
| ⑦ | 快进倍速切换（1× ↔ 2×） | 无 | 跑 | 跑（cap 随速度变） | 不飞 | 不飞 |
| ⑧ | 打开住户对话框 | 无（`#scr-live` 仍 active） | 跑 | 跑 | 不飞 | 不飞 |
| ⑨ | 主线程长任务阻塞（剪辑页重渲染 / 存档落盘 / AI 回包） | 无（rAF 延后一帧） | 跑（dt 被 `Math.min(0.1,…)` 封顶） | 跑（同一个 dt） | 不飞 | 不飞 |

**逐条实测结论与依据**：

- **①切页 —— 唯一会飞的一种。** 实测停摆 2/5/10/30/60 秒，恢复后最大单帧显示位移
  恒为 **0.19167 格（1×）／0.28333 格（2×）**＝阈值的 1.99／1.47 倍；
  停摆瞬间真显差最大 **36.35 格**；脚底逐帧落进 `PIX_SOLID` 实体格最多 **35 帧**
  （如 `13,7 14,7 15,7 16,7 17,7 18,7 19,7` 一整排被一根直线扫穿）。
- **②标签页切走／最小化 —— 不飞，理由是结构性的。** rAF 被暂停时第 3、4、8 步一起停，
  两者同冻结。**且即使浏览器改成低频节流而非全停也照样不飞**：
  `dtFrame=Math.min(0.1,…)` 把单帧封顶在 0.1 秒，
  而 `updateWalkers` 与 `stepDisplay` 吃的是**同一个 `dtFrame`**——
  世界只会整体变慢，两者不会拉开。故本条结论不依赖具体浏览器的节流策略。
- **③失焦 —— 不飞，同②的后半段理由**（按最坏情形 10fps 建模，即 `dt` 拉到封顶值 0.1）。
- **④存档载入 —— 不飞。** 导入存档走 `setTimeout(()=>location.reload(),300)`（`:2278`），
  整页重载 ⇒ `state.vis` 在 `:1707` 重建，`v.spot===undefined` ⇒ 首帧落位打 `warp` 标直置。
  这是第 20 单白名单里的第一处，**是直置不是补间，不画线，故不存在穿墙**。
- **⑤暂停后恢复 —— 不飞。** `w.speed=0` ⇒ `Sim.step` 被 `if(w.speed>0)` 跳过、
  `updateWalkers` 的 `mult=0` 使 `budget=0`，真实位冻结；而 `draw()` 照跑，
  显示位追上后即与真实位重合。**顺带查清一处可疑点**：暂停时 `v.moving` 变假，
  会触发 `stepDisplay` 里 `usePix && !v.moving` 的兜底钳制 `pixStandPos`——
  但该函数首行即 `if(!PIX_SOLID.has(脚底格)) return {x:v.x,y:v.y}`，
  而走线已保证脚底格非实体格，故**恒为空操作**（门禁逐帧断言 `clampHits===0`）。虚惊。
- **⑥reduceMotion —— 不飞，而且它恰好把病症盖住了。** 开着 reduceMotion 时锚变即直置，
  切页期间攒下的不是「一段要补的距离」而是「一个待消费的 warp 标」，
  切回时一次性直置到位。**这意味着开着 reduceMotion 的用户看不到本病症**——
  复现本病症必须关掉它。
- **⑦倍速切换 —— 不飞。** 不涉及停摆；`cap` 与阈值同时随 `speed` 缩放，比值不变。
- **⑧对话框 —— 不飞。** 对话框是 `#dialog-root` 覆盖层，`#scr-live` 仍 `active`，`draw()` 照跑。
- **⑨主线程长任务 —— 不飞，理由同②后半段。**

**普查的一般结论**：治前全站**只有 ①切页 一处**把「真实位推进」与「显示位推进」拆到了
两个不同的开关上；其余八种要么整条主循环一起停，要么根本不停。
治后连这一处也没有了——显示位推进被移到与真实位推进**同一个无条件位置**，
两者从结构上再也无法分开。

## 2. 治法

### 2.1 落的是哪一档

任务书第一优先档写的是「恢复渲染时直接对齐，不做补间」。
本单实现达到的是**同一个目的的更强形式**：**让落差压根不产生，因而无需对齐。**

```js
// city-life-framework.html（新增）
function stepAllDisplays(dtSec){
  const pixOn=pix.on&&pix.ready;
  for(const ag of state.world.agents) stepDisplay(ag,dtSec,pixOn);
}

// loop() 内
  updateWalkers(dtFrame);
  stepAllDisplays(dtFrame);   // ← 显示位每帧必推，与当前在哪一页无关
  updateCamera(dtFrame);

// draw() 内：由「推进并取用」改为「只取用」
  const dispPos={};
  for(const ag of state.world.agents){
    const v=state.vis[ag.id];            // 治前是 const v=stepDisplay(ag,dtFrame,pixOn);
    dispPos[ag.id]={x:v.dspX,y:v.dspY};
  }
```

**为什么这比「切回时直置」更好，逐条**：

1. **玩家看到的结果完全一致**——切回那一刻人就在该在的地方，不播放任何移动过程。
2. **不新增任何直置通道**。任务书点名要防「打个标就能瞬移」的后门。
   「切回时直置」这一路必然要引入第三个 warp 来源（第 20 单白名单只有两处），
   而白名单一旦从 2 涨到 3，第 20 单那条「warp 恰等于住户人数」的硬断言就得放宽。
   本方案 **`v.warp` 的置位处逐字未动**，那条断言原封不动地继续成立。
3. **切回后看到的是真的在走路**，不是「刚被瞬移到位然后开始走」——
   显示位在离开期间一直如实跟着真实位，返回时是这段连续运动的自然延续。
4. **代价为零**：多算的只是每帧 4 个住户的两次减法与一次 `hypot`。

### 2.2 为什么没有采用第二优先的「离开时长阈值」

任务书写「**若**某些情形下直置观感突兀（例如只切走两秒），可设一个离开时长阈值」。
**本方案不存在直置，也就不存在突兀**：不论离开 2 秒还是 60 秒，
切回时显示位与真实位都已重合（真显差恒为 0），没有任何需要在「平滑」与「直置」之间二选一的时刻。
故该档**无适用场景，未引入任何新常量**——这也避免了多一个可调阈值就多一处要对账的地方。

### 2.3 硬红线自查

> 硬红线：任何情形下都不许出现「显示坐标沿直线穿过实体或家具」。

治后**全站九种情形逐帧实测：脚底格落入 `PIX_SOLID` 共 0 帧**（见 §3 门禁读数）。
更强的保证是结构性的：显示位恒等于真实位，而真实位由 `buildPath` 产出的避实体折线驱动
（第 20 单规矩二已逐帧＋逐段断言其不穿实体）。
**显示位不再有任何独立于寻路结果的运动自由度**，故不存在「自己划一根线」的可能。

## 3. 本单补的闸

`walkgate.js` 新增「渲染停摆普查」一节，**42 条断言**（全文件 ok 总数 37 → 79）。

### 3.1 新判据：真显差恒零

```
|真实位 − 显示位| ≤ 1e-9，在每一个真正出画的帧上
```

**为什么要新立这一条**：落差本身就是病，不必等它变成超限位移才报。
治前那 36 格的落差在**任何单帧里都不违反铁律一**（限速器把它切成了每帧 0.19 格），
只有把「落差」直接立成判据，才能在它变成一段飞行之前就抓住。

### 3.2 采样范围扩张：七种停摆情形 × 四条断言

每种情形复演成「主循环的哪几步被跳过」，逐帧验：
①真显差恒零　②相邻两画面位移 ≤ 阈值　③脚底零落实体格　④直置零出白名单。

