## 一、病症一：家具遮挡人物

### 1.1 第一问先答：人物与家具的绘制次序由什么决定？

**答：有深度排序，按脚底 y 统一排序，且工作正常。**

`draw()` 把「四个小人」与「七件高件家具」放进同一个数组，按脚底 y 升序排，靠下者后画：

```js
const ents=state.world.agents.map(ag=>({kind:'a',ag,fy:dispPos[ag.id].y+0.5}));
if(pixOn) for(const f of PIX_FURN_TALL) ents.push({kind:'f',f,fy:f[4]});
ents.sort((a,b)=>a.fy-b.fy);
```

`PIX_FURN_TALL` 的第 5 个字段就是该件家具的脚底世界 y，与 `tools/asset-pipeline/build_assets.py`
的 `GAME_FURN_TALL` 登记表联动。**所以这不是排序缺陷。**

### 1.2 那是什么缺陷：站位选点

全部 7 个多人锚 × 28 个站位 × 7 件高件家具逐对求交，**只有一处翻车**：

```
✗遮挡 home_table#1 落点(2.5,9.5) 脚底y=10 vs table(脚底10.813) 重叠 0.396×1.500 格 = 包围盒 29.7%
○在前 home_tv#0   落点(3.2,7)   脚底y=7.5 vs sofa (脚底7.292)  重叠 1.000×1.688 格 = 包围盒 84.4%
○在前 home_tv#1   落点(1.7,7)   脚底y=7.5 vs sofa (脚底7.292)  重叠 0.700×1.688 格 = 包围盒 59.1%
○在前 home_tv#2   落点(4.7,7)   脚底y=7.5 vs sofa (脚底7.292)  重叠 0.300×1.688 格 = 包围盒 25.3%
○在前 kitchen#0   落点(14.1,9.5) 脚底y=10 vs stove(脚底9.563)  重叠 0.692×1.563 格 = 包围盒 54.0%
○在前 kitchen#0   落点(14.1,9.5) 脚底y=10 vs counter(脚底8.688) 重叠 0.267×0.688 格 = 包围盒 9.2%
○在前 kitchen#1   落点(15.6,9.5) 脚底y=10 vs counter(脚底8.688) 重叠 1.000×0.688 格 = 包围盒 34.4%
○在前 kitchen#3   落点(18.6,10.5) 脚底y=11 vs fridge(脚底10.063) 重叠 0.704×1.063 格 = 包围盒 37.4%
```

八处相交里七处正确（人在家具之前），只有餐桌左席 `[-3,0]` 落在 (2.5, 9.5)，
脚底 y=10.0 **小于**餐桌脚底 y=10.813 —— 排序把餐桌排在它后面画，于是盖住人身 29.7%（且盖的是下半身）。

**这是选点缺陷**：左席被选在了餐桌「身后」的那一行。第 19 单其实**知道**这条规矩——
`kitchen` 站位表的原注释写着「冰箱脚底 y=10.063，故后两位下压 1 格，保证人物脚底 y 大于冰箱脚底」——
**对冰箱做了，对餐桌漏了**，而 5.3 的合规自查只校验「脚底格非 PIX_SOLID」与「包围盒在房内」，
两条都查不出这一条，于是漏网。

### 1.3 为什么 v30 之前不出现

v30 之前四人全叠在零偏移点 (5.5, 9.5)，精灵横跨 x∈[5.0, 6.0]；
餐桌绘制矩形 x∈[2.604, 4.979] —— **横向差 0.021 格擦身而过，零相交**，家具再怎么后画也盖不到。
故本单确系 v30 引入，决策者判断正确。

### 1.4 治法与判据

左席 `[-3,0]` → `[-3,1.5]`，落点 (2.5, 11.0)、脚底 y=11.5 > 10.813，人画在桌之前，观感即「站在餐桌左前方」。
同时**把漏掉的那条判据补进站位表口径④并落成门禁**：

> 站位精灵包围盒若与高件家具绘制矩形相交，则该站位脚底 y 必须**严格大于**该家具脚底 y。

门禁读数：`与家具相交的 8 个站位全部画在家具之前（被盖住 0 处；最薄一处余量 0.208 格：home_tv#0 vs sofa）`

改后新落点对第 19 单原有五条几何自检全部照过（脚底格 (2,11) 非实体、包围盒在客厅内、
与同房间可同时在场的落点两两 ≥1 格、零名牌压人身）——见 `node harness.js` 全绿。

## 二、病症二：瞬移

### 2.1 参谋假说的哪一条成立

假说给了两个可能：「至少有一条路径绕过了平滑器」或「平滑器的限速对 4.5 格量级不起作用」。
**实测是第一条，而且那条路径就写在平滑器自己身上：**

```js
if(v.dspX===undefined || Math.hypot(tx-v.dspX,ty-v.dspY)>3){ v.dspX=tx; v.dspY=ty; }   // 初始化/传送级跳变直置
```

这行的本意是「位移大到不可能是走路，那必是传送，直置」。它**按距离猜意图**，
而 `kitchen` 站位表第 4 位的偏移 `[4.5,1]` 长度 4.610 格 —— 一贴上就命中旁路，限速器根本没被调用。

### 2.2 比假说更严重：连 3 格的偏移也照样溜过去

逐帧实测（双种子 × 双速度 × 3 天 @60fps，复演主循环调用序）：

| 触发锚 | 直置次数（seed 20260803, 1×, 3 天） | 最大单帧位移 |
|---|---|---|
| kitchen | 11 | 4.639 格 |
| home_table | 6 | 4.640 格 |
| home_tv | 4 | 4.640 格 |
| home_desk | 3 | 4.640 格 |
| store_counter | 3 | 3.042 格 |
| bed2 / bed3 / bed4 | 各 1 | 3.090 / 3.183 / 4.640 格 |
| **合计** | **30 次 / 3 天** | **4.640 格** |

注意 `bed2` `bed3` `store_counter` 这些**零偏移或 3 格偏移**的锚也在榜上：
起步那一帧路径刚铺好、偏移被撤销，同时 `updateWalkers` 已经把 `v.x` 往前推了本帧的一小步，
两者相加**刚好越过 3**。所以不是「只有厨房那一处会瞬移」——**几乎每一次离位都瞬移**，
只是幅度不同。这正对得上决策者「上座、下座、厨房就位与离位，均出现位置跳变」的实证。

**对照组（把站位偏移整个关掉，≈v30 前）：直置 0 次。** 全部 30–69 次跳变都由站位偏移的贴／撤引起。

手动逐帧驱动（冻结 rAF ＋ 冻结 `Sim.step`，两份源码跑同一段时间轴、逐帧可对齐），
按「走到、`v.path` 清空」这一语义时刻对齐 before/after：

- **厨房就位**：`docs/交付/第20单-图/对照-病症二-厨房就位.png`
  改前 帧101→帧102：(14.10, 9.51) → (18.60, 10.50)，**一帧 4.61 格**。
  改后 全程峰值单帧位移 **0.092 格**。
- **上座**：`docs/交付/第20单-图/对照-病症二-上座.png`
  改前 帧188→帧189：(5.57, 9.51) → (2.50, 9.50)，**一帧 3.07 格**。
  改后 全程峰值单帧位移 **0.092 格**。

### 2.4 治法：走任务书第一优先档

**站位成为寻路的真终点与真起点。**

1. `buildPath(fromX, fromY, toAnchorId, spot)` 的终点由 `锚点显示点 + 站位偏移` 算出，锚点中心不再是终点。
2. 起点恒取 `v.x / v.y` ＝人当前实际所在处（原文本就如此，站位并入后它才**真的**是人所在处）。
3. `draw()` 里「贴偏移」那两行删除；显示坐标的产出收口成一个函数 `stepDisplay()`。
4. 平滑器的距离旁路拆除，改认显式 `v.warp` 标 —— 只有任务书明列豁免的两处会设它：
   **首帧落位**与 **reduceMotion 直置**。存档载入不设：载入后锚变了就正常走过去，不再瞬移。

如此则「贴上／撤销偏移」这个动作**不存在了**，跳变从结构上消失，而非被限速掩盖。

**第一档确实做得到，故未启用第二档。**

### 3.2 治法：避实体走线

因为本单要立「规矩二·全程不得穿实体」，这笔老账必须一并还掉，否则闸立不起来。新增渲染层三个小函数：

- `segHitsSolid(ax,ay,bx,by)`：按 0.02 格步长采样线段的脚底轨迹（远细于单帧步长上限 0.19 格，
  故采样漏检不可能反过来被逐帧门禁看见）。
- `bfsAround(...)`：在非实体脚底格上做四邻域 BFS，邻域序写死＝确定性的唯一来源，零 rng 零状态。
- `avoidSolids(fromX,fromY,pts)`：**只对撞上实体格的那一段改线**，其余段逐字保持原样；
  改线后做拉绳简化（每次取还能直达的最远航点），故不出锯齿。

`buildPath` 拆成 `buildPath = avoidSolids(buildPathRaw(...))`，原文逻辑一行未动地留在 `buildPathRaw` 里。
`PIX_SOLID` 全部落在 `APT` 内，故楼外（街面／公园／广场／步道）走线永不触发本段，**B 案骨架判例零影响**。

## 四、本单立的三条铁律（门禁 `walkgate.js`，已进 CI）

判据与阈值由施工拟定，理由随条列出。三条一并写进《交接说明》踩坑备忘。

### 规矩一 · 逐帧位移上限

**判据**：正常运行（非首帧落位、非 reduceMotion 直置）下，任一人物**显示坐标**在相邻两帧之间的位移
≤ `行走速率 5.5 格/秒 × 速度档 × dt × 1.05`。

**为什么这样立**：把上限直接绑在「人腿能走多快」上，而不是拍一个绝对数字。
绝对数字会随帧率与速度档失效（掉帧到 10fps 时 1.1 格是合法的，60fps 时 0.19 格就该报警），
而「一帧走的距离不得超过这一帧里腿能走的距离」在任何帧率、任何速度档下都成立。
1.05 只是浮点余量——实测值**恒等于**理论上限本身，说明限速器从未成为瓶颈，显示位一步不多走。

**为什么还要一条绝对上限**：主循环把 `dtFrame` 封顶在 0.1 秒、速度档最高 2×，
故任何情形下单帧位移都不得超过 `5.5 × 2 × 0.1 × 1.05 = 1.155 格`。这一条才是「瞬移」的正面判据。

**豁免通道不许被滥用**：门禁额外断言 warp 直置**恰好等于住户人数**（每人首帧落位一次），
多一次都算违规——否则「打个 warp 标就能瞬移」会变成新的后门。

**实测读数**（双种子 × 双速度 × 两档 dt × 3 天，共采样 **483,840 人帧**）：

| dt | 速度 | 实测最大单帧位移 | 阈值 | 余量 |
|---|---|---|---|---|
| 1/60 s | 1× | **0.09167 格** | 0.09625 格 | 4.8% |
| 1/60 s | 2× | **0.18333 格** | 0.19250 格 | 4.8% |
| 0.1 s | 1× | **0.55000 格** | 0.57750 格 | 4.8% |
| 0.1 s | 2× | **1.10000 格** | 1.15500 格 | 4.8% |

绝对上限：阈值 **1.155 格**，实测最坏 **1.100 格**，余量 0.055 格＝4.8%。
**本单前同口径实测 4.671 格 —— 直接击穿。**
warp 直置：每档恰 4 次＝每人首帧落位一次。

### 规矩二 · 全程不得穿实体

**判据**：`PIX_SOLID`。这就是「家具占格」的权威登记——它由
`tools/asset-pipeline/build_assets.py` 的 `GAME_SOLID_CELLS` 生成，与 `GAME_FURN_TALL` 同表联动，
逐格登记了墙带与每件家具的占格，比「用家具绘制矩形当禁区」精确（矩形是含空白的包围盒）。
移动全程与静止落位一视同仁，第 19 单只校验静止的口径本单作废。

**两层校验**（缺一不可）：
1. **逐帧**：每一帧每个人的脚底格不得落在 `PIX_SOLID`。
2. **逐线**：每条新铺走线的折线自身，按 0.02 格采样不得穿实体。
   —— 只查逐帧会漏：60fps 下单帧步长 0.09 格，理论上可能跨过一格薄片而不落在里面；
   逐线采样比单帧步长细近 5 倍，堵掉这个缝。

**额外一条（本单排查中发现的隐患）**：竖向墙体**不在** `PIX_SOLID` 里
（登记表只收墙带与家具占格），所以「不踩实体格」并**不蕴含**「不穿墙」。
故单独断言：避实体改线造出的航点必须全部落在房间内。

**实测读数**：
- 逐帧脚底格零落入实体格（采样 **483,840 人帧**，命中 **0** 帧）。本单前同口径：1059–1316 帧/3 天/种子。
- 每条新铺走线折线零穿实体（**819** 次铺路、**3574** 个航点，越界 **0** 段）。
- 兜底钳制 `pixStandPos` 生效 **0** 次（恒为空操作）。
- 避实体改线航点零穿墙（越界 **0** 处）。

**如实上报一处，未修**：走线途经的最窄净宽 **1 格**（客厅 `1,9`，491 人帧，占 0.101%）。
成因是第 11 单甲案客厅放样——餐桌左椅占格 `(2,9)`，与客厅西墙之间只剩 1 格。
《云港建筑规范》二.1「单人通道 ≥2 格」、二.2「宽 1 格的通道是零余量下限，放样时一律不得按 1 格通道设计」
管的是**放样**；本单不动放样（动了就要改房间/家具几何、连带素材流水线与指纹），
故只作为读数上报并入待办，不静默吞掉。走线本身合法：脚底零进实体格，人宽 42–48px 可通过。

### 规矩三 · 显示位置只有一个来源

**判据**：显示坐标不得由「寻路结果」与「渲染期偏移」两处叠加产生。落成**源码原文的反向断言**：

| 断言 | 实测 |
|---|---|
| `draw()` 对 `standSpot` / `STAND_SPOTS` 零引用 | 0 处 |
| `stepDisplay` 对站位表零引用 | 0 处 |
| `v.dspX` / `v.dspY` 的写入全部落在 `stepDisplay` 一处 | 全渲染层 6 处 = `stepDisplay` 内 6 处 |
| `standSpot` 全渲染层仅 1 个调用点，且在 `updateWalkers` 内 | 1 处 |
| `buildPath` 的终点参数直接收站位 | 命中 |
| `buildPathRaw` 的 target 由「锚点显示点＋站位」算出 | 命中 |
| 距离旁路 `Math.hypot(...)>3` 已拆除 | 已拆 |
| 直置只认显式 `warp` 标 | 命中 |
| `v.warp` 全渲染层仅 1 处置位 | 1 处 |

**为什么判据要立在源码原文上**：这条规矩防的是**写法**，不是某个数值。
行为断言（规矩一）只能证明「这一版没跳」，挡不住下一单有人再写一次「绘制期贴个偏移」——
只要偏移小于旁路阈值，行为断言就抓不到。所以必须直接反向断言那种写法不存在。
