# 第 61 单 · 「到点结算」的读写次序普查（先快照 → 再清账 → 再派活）

> 一句话：第 60 单抓到的那处 bug（先清账后读账）**不是孤例风险，而是一类**——
> 本单把世界上所有"到点会重置某笔账"的地方逐个查了一遍，**把周的账收成一个读出口**（`weekSnapshot`），
> 并把十一处清账点的次序写成机器闸。**没再发现第二处真 bug**（照实说），但从此这类错会被门禁挡住。

## 一 · 起因（第 60 单的账）

第 60 单在扩目标池时，第 53 单那条"短信影响挑目标"的行为闸判红了。追下去是**次序**：

```
goalStep 到点（周一 08:00）：weekMemory(w,ag) → goalAssign(w,ag)
                             ↑ 这一步把 ag.week 清账（含 smsId）
```

于是一年中有一半的周，短信记录在"派活"之前就被清掉了——**当年那条闸是靠运气过的**。
修法（第 60 单）是把读提前；本单把它**结构**化：读只有一个出口。

## 二 · 治法：把"读"收成一个出口

```js
function weekSnapshot(ag){ /* 周账的唯一读出口：信／smsId／smsLabel／结局／班／出／聊 */ }
function weekMemory(w,ag,snap){ const s=snap||weekSnapshot(ag); … }   // 自己不再直接读 ag.week
// 到点结算三步：先快照 → 再清账 → 再派活
const snap=weekSnapshot(ag);
if(该记) weekMemory(w,ag,snap);
g=goalAssign(w,ag,snap.smsId);
```

为什么这么改而不是"再小心一点"：**注释约定挡不住第二个人**。现在"读周账"这件事在源码里只有一条路，
谁把次序改回去，门禁的三条结构断言会当场判红（见第四节）。

## 三 · 普查：十一处"到点清账"逐个过

判据统一是**"读在清之前"**：清账点之后还有没有代码去读同一笔账、拿到的会不会已经是新一轮的值。

| # | 清账点（到点重置的东西） | 读点在哪 | 次序 | 核实方式 |
|---|---|---|---|---|
| 1 | 每日 00:00 `w.credits=3; w.sentToday=[]` | 玩家发短信、手机页 | ✅ 先判后清 | 源码闸 |
| 2 | 每月 2 号 08:00 交租（`w.rentPaidDay=day`） | 防重复交租 | ✅ 先判后写 | 源码闸 |
| 3 | 周五 18:00 发薪（`w.stats.pay++`） | — | ✅ 无读 | 源码闸 |
| 4 | 雨停（`w.weather.rain=false`） | 判 `until` 到点 | ✅ 先判后清 | 源码闸 |
| 5 | 夜市换周／开张（`nmNotice/nmCount` 归零） | 收摊播报读 `nmCount` | ✅ 归零只两处、读在最后 | 源码闸（计数＝2） |
| 6 | 晨报日号（`w.morningDay=d`） | 防同日重复 | ✅ 先判后写 | 源码闸 |
| 7 | **周账**（`weekMemory` 写新周） | `goalAssign` 读短信 | ✅ **本单改成"先快照"** | 源码闸 ＋ 行为闸 |
| 8 | 剪辑日切（建新窗） | 结旧窗 | ✅ 先算旧、再建新 | 源码闸 |
| 9 | `pickV` 跨天（重置当日去重） | 抽词 | ✅ 先判天号再清 | 源码闸 |
| 10 | 离线追帧水位线（`aiFloorLid`，开局记一次） | 落字筛选 | ✅ 只写一次、只读 | 源码闸 |
| 11 | 导演层"有戏"（`lastSpark`，第 58 单修过） | 雨判据 | ✅ 只看本拍新落条目 | 第 58 单的闸 |

**结论：十一处里没有第二处真 bug。** 但第 7 处（周账）原先只是"这次改对了"，
本单把它变成了"改不回去"——这是本单的主要产出。

## 四 · 门禁（九条，全部进 `harness.js`）

1. `weekSnapshot` 一处定义（周账唯一读出口）；
2. `weekMemory` 在清账之前**不直接读** `ag.week`；
3. 到点结算三步钉死（快照 → 清账 → 派活，且 `goalAssign` 吃 `snap.smsId`）；
4. 剪辑日切**先算旧窗再建新窗**；
5. `pickV` 跨天判定在重置之前；
6. 雨停先判 `until` 再清标；
7. 夜市到客数**只两处归零**（换周／开张）；
8. **清账点清单逐条对得上源码**（十一处各一条正则——防"删了清账点却没登记"）；
9. 行为侧：15 天里周记忆 8 条（2 批 × 4 人）、格式全对（快照改法没把内容弄丢）。

## 七 · 已知接受项与盲区（照实登记，不粉饰）

1. **这次只查了"到点型"清账**（按时刻触发的那一类）。还有一类是**"事件型覆盖"**：
   同一笔账被后来的事件覆盖（例如 `ag.sit` 每人只挂一条处境、`ag.lastGoalOut` 每人只留最后一次结局）
   ——那不是次序错，是**设计上的取舍**，但如果一天里真的出两次，前一次就不会上卡。
   本单没改这个行为，只把它记在这里（要改成队列是另一单）。
2. **清单靠人工维护**：新增一处"到点清账"必须回写第三节那张表与第 8 条断言里的正则，
   （照第 34 单立的口径：能写成机器闸的就写成机器闸——本单已经这么做了，但"清单里该有几条"仍需人加）。
3. **`weekSnapshot` 的字段是手抄的**：将来往周账里加字段，要记得同步加进快照（否则下游读不到）。
   已在这段源码注释里写明。
4. 第 39 单那笔**冷读测试欠账仍未补**。
