## 零、结论摘要（一页看完）

1. **病因证实**：参谋的假说成立，且比假说更彻底——
   `ANCHORS` 确实是「一功能一点」，同一活动的多名住户被派到同一个锚点；
   **落位逻辑里没有任何占用检查／让位／排队**（全文检索确认，全仓唯一的 queue 是 AI 请求队列）；
   而**显示坐标是由锚点几何直算出来的**（`v.x=a.x+0.5`、`v.y=a.y+0.5`），**逐人零区分**，
   所以 N 个人不是「挨得近」，是**渲染到同一个像素**，只看得见最后画的那一个。
2. **不止两处**：决策者说得对。可停留的 15 个锚点里，**7 个**理论上能被多人同占，
   30 天双种子实测**全部真实发生过**（普查表见第三章）。客厅与厨房只是最显眼的两处。
3. **稳定复现，不是偶发**：30 天窗口里 **20.3% / 20.7% 的拍**至少有一处在叠人；
   客厅两处**几乎天天发生**（30/30 与 29–31/30 天），最长一次连续叠 **190 分钟**。
4. **治法落在任务书第一优先档（纯显示层错开）**，且**七处全部适用**，不需要动 SIM。
   缘由见第四章：第 11 单已把「坐标与规则解耦」做实——SIM 只认锚名，坐标只有渲染层消费，
   所以「给一个功能位补足落脚点」这件事**整件可以在显示层完成**，第二档因此塌缩进第一档。
5. **代价**：SIM 零改动、rng 零位移、`ANCHORS` 零改动。
   **sim30 双种子指纹逐字节一致**（改前改后同为 `4061fd2ef23a8dd927345785065a69e5`），
   六项阈值一行未动，「30 天生存不变量」零风险——**没有任何角色因为让位而做不成活动，因为本单根本没有让位逻辑**。

## 一、第 1 问：角色的显示坐标由哪一步决定？

**答：由渲染层就地取的，SIM 不产出坐标。**

链路逐段（皆在 `city-life-framework.html`）：

| 段 | 位置 | 做了什么 |
|---|---|---|
| ① SIM 决策 | `decide()` / `setActivity()` | 只写 `ag.anchor = 锚名字符串`。**SIM 全程不产出任何 x/y。** |
| ② 渲染层建行走态 | `state.vis[ag.id]={x:a.x+0.5, y:a.y+0.5, …}` | 初始化时直接由锚点几何算出显示点 |
| ③ 走路插值 | `updateWalkers()` | `v.anchor!==ag.anchor` 即重铺路径 `buildPath()`；走到即 `v.x=p.x, v.y=p.y`，**终点恒等于 `a.x+0.5, a.y+0.5`** |
| ④ 落位钳制 | `pixStandPos(v)` | 静止时若脚底格落在 `PIX_SOLID` 就近钳到可站格 |
| ⑤ 平滑器 | `v.dspX / v.dspY` | 钳制切换走限速滑动，禁跨格瞬现 |
| ⑥ 落笔 | `draw()` | `dx0=px-dw/2, dy0=py+s*0.5-dh`，脚底贴格底 |

**关键点：②③④⑤⑥ 全过程零「人」的参与**——同一个 `ag.anchor` 进去，出来的显示点逐位相同。
四个人站同一个锚点，四个精灵画在同一个像素上。

**并且第 ④ 步（钳制器）救不了这个病**：实测全部 15 个锚点的脚底格**没有一个**落在 `PIX_SOLID` 里，
`pixStandPos` 对所有锚点都是空操作：

```
home_table 锚(5,9)      显示(5.50,9.50)  脚底格(5,10)  钳制空操作
home_tv    锚(2.7,6.5)  显示(3.20,7.00)  脚底格(3,7)   钳制空操作
kitchen    锚(13.6,9)   显示(14.10,9.50) 脚底格(14,10) 钳制空操作
…（15 个锚点逐一验过，无一命中实体格）
```

顺带说清「客厅那张凳子」是哪一张：餐桌整件占世界格 (3–4, 8–10)，
左椅登记在格 (2,9)、右椅在格 (5,9)。`home_table` 的显示点 (5.5, 9.5) 使精灵身体正好盖住格 (5,9)
——**就是右边那张凳子**。四个人全画在它上面，就是决策者看到的样子。

## 二、第 2 问：现有落位逻辑里有没有占用检查／让位／排队？

**答：没有。一处都没有。**

- 全文检索 `occup / taken / queue / 排队 / 让位 / 占用 / reserve / slot / seat / 空位`：
  命中项只有三类，**全部与落位无关**——AI 请求队列（`llmQueue`/`queueCall`/`pumpLLM`）、
  街市独白文案里的「排队最长的那家」、素材加载回调。
- `setActivity(w,ag,anchorId,…)` 的全身只有五行：写统计、判是否换地点、写 `ag.anchor`、写 `ag.activity`、
  写 `ag.busyUntil`。**没有一行去问「这个锚点上已经有人了吗」。**
- `decide()` 里选落脚点的四个分支（吃饭、上班、散步、在家待着）也一样：
  `ag.workAnchor` / `ag.bed` 是逐人写死的常量，`kitchen`/`store_counter`/`market` 是写死的字符串，
  `home_table|home_tv` 与 `park_bench|river_walk` 是 `w.rng()<0.5` 二选一——**掷骰子，不看有没有人**。

所以两个人同时被派到一张凳子上，不是「判断失误」，是**系统里压根没有这个判断**。

## 四、第 4 问：稳定复现还是偶发？

**答：稳定复现，且是全天候的。**

| 种子 | 至少一处在叠人的拍数 | 占比 | 覆盖天数 | 最长连续 |
|---|---|---|---|---|
| `20260803` | 878 / 4320 | **20.3%** | 30 天全覆盖 | 19 拍＝**190 分钟** |
| `424242` | 895 / 4320 | **20.7%** | 30 天全覆盖 | 15 拍＝**150 分钟** |

分层看：
- **客厅两处是天天发生**（`home_table` 30/30 与 31/31 天；`home_tv` 30 与 29 天），
  两者合计占了全部重叠拍数的四分之三以上——与决策者「客厅最先看见」的实测完全吻合。
- **厨房与便利店是隔天量级**（17–26 天）——决策者点名厨房，也吻合。
- **公园／江边／街市是偶发**（3–8 天），但**确实存在**，且街市那 4 天全在周日
  （只有周日才有街市分支），一旦碰上就是三个人叠在一起。这正是决策者说的「还有其他好几个地方」。

结论：这不是随机抖动，是**结构性必然**——只要两个人同时选中同一个兜底分支就必然叠，
而「在家待着」和「散步」都是二选一的兜底，四个人撞在一起的概率本来就很高。

## 五、治法：落在第一优先档（纯显示层错开）

### 5.1 为什么第一档成立，而且七处全部成立

任务书第一档的判据是「两人同处一个功能位在设定上本就合理」。逐点核对：

| 锚点 | 功能位实体 | 两人以上同处是否合理 | 判定 |
|---|---|---|---|
| `home_table` | 餐桌＋三把椅子（左椅格 2,9／右椅格 5,9／北椅） | 合租室友围一张餐桌，合理 | 第一档 |
| `home_tv` | 沙发横跨列 1–4（至少三座） | 任务书原文举的例子就是「同一张沙发坐两人」 | 第一档 |
| `kitchen` | 灶台（13–14,8–9）＋台面（15–16,8）＋冰箱（18–19,8–9） | 任务书原文举的例子就是「一人炒一人洗」 | 第一档 |
| `store_counter` | 便利店收银台 | 一人当班＋几人排队买饭，合理 | 第一档 |
| `park_bench` | 公园长椅 | 长椅本就坐得下两三人 | 第一档 |
| `river_walk` | 江边步道 | 步道是带状公共空间 | 第一档 |
| `market` | 周日街市（广场 T 竖净道） | 街市本就是人多的地方 | 第一档 |

**第二档为什么用不上（这是本单最关键的一条机理）**：
任务书第二档写的是「给该功能补足落脚点数量，按人数分配」。
但第 11 单已把**坐标与规则解耦**做实并写进《云港建筑规范》——
**SIM 决策只经房间名／锚名，`ROOMS`/`ANCHORS` 的坐标数字仅渲染层消费**。
所以「给一个功能补足落脚点」这件事，**整件可以在渲染层完成**：
给同一个锚点登记四个像素落点，效果与「补四个锚点」完全一样，而且

- 不必往 `ANCHORS` 加条目（`ANCHORS` 是 SIM 块的硬编码名单，加条目要动 SIM 导出与门禁真值断言）；
- 不必改 `decide()` 的派活分支（那才是真正会位移 rng 流、炸指纹的地方）；
- 不必引入任何占用查询。

**第二档因此塌缩进第一档，第三档（占用检查与让位）自然无从谈起。**
顺带把任务书的红线交代清楚：本单**没有任何让位逻辑**，
所以「占用冲突导致角色做不成活动」这个失败模式**在本单结构上不可能发生**——
角色照旧该吃吃、该睡睡、该上班上班，`ag.anchor` 与 `ag.activity` 一位没变。

### 5.2 具体做法

新增 DOM 层登记表 **`STAND_SPOTS`**（锚名 → 四个「相对该锚显示点的格偏移」）与派活函数 `standSpot(ag)`：

```
home_table    [[0,0],[-3,0],[1.5,0],[3,0]]          右椅（现状位）／左椅／桌东两位，四人同排
home_tv       [[0,0],[-1.5,0],[1.5,0],[3,0]]        顺沙发排开三座＋沙发东侧站位
kitchen       [[0,0],[1.5,0],[3,1],[4.5,1]]         灶台前／台面前／冰箱前两位
store_counter [[0,0],[1.5,0],[3,0],[-1.5,0]]        台前一人＋左右排开
park_bench    [[0,0],[1.5,0],[-1.5,0],[3,0]]        顺长椅横排
river_walk    [[0,0],[1.5,0],[-1.5,0],[3,0]]        顺步道横排
market        [[0,0],[-1,2.5],[1,2.5],[0,-2.5]]     T 竖净道只有 3 格宽，横排摆不下，改「前一后二加北一」
```

三条口径写死在代码注释里：

1. **按住户在 `agents` 数组中的固定下标分配**——零 rng、零状态、零占用查询。
   由此得两个性质：同一锚点的任意两人**恒取不同站位**；
   一个人的站位**不因别人来去而移动**（不会出现「有人来了大家互相挪窝」的鬼畜观感）。
2. **只在「已走到」时生效**（判据是 `v.path` 空，不是 `v.moving` 为假——
   半路按暂停时 `v.moving` 也是假，那种情形不得偏移，否则一按暂停人就横移）。
   行进中零偏移，显示照旧＝SIM 插值原样，沿用补充指令四口径；切换仍走既有平滑器限速滑动。
3. **登记的是相对偏移不是绝对坐标**——`ROOMS`/`ANCHORS` 日后迁址自动跟随，无第二处硬编码。

另改一处配套：画布点选测距原先只在像素画风下认平滑显示位，现改为**两条渲染路径都认**
（旧色块渲染下 `dspX` 恒等于显示落点），否则错开后点人会点不准。

### 5.3 放样合规自查（对照《云港建筑规范》与《云港城市总规》）

| 判据 | 依据 | 结果 |
|---|---|---|
| 站位脚底格不得落在实体格 | 补充指令三 `PIX_SOLID`（人物脚底不得落入显示） | 28 个站位**零命中**，钳制器恒为空操作 |

# 第十章 · 追加一：时间戳跨天混叠

## 10.1 病症与病根

决策者实测（v29 线上，D75 白一鸣短信页「往来记录」）：条目呈现为
`04:40 / 05:40 / 06:30 / 03:30 / 04:20 …`，看似时间倒流；
按「剩余额度」可还原为三个不同日子（每日 3 条、日日重置）。

病根一句话：**列表只印 HH:MM 不印日期**。条目本身按 `e.t` 严格升序，
渲染时 `PURE.fmtTime(t)` 只取 `t % 1440`，日期信息在渲染这一步被丢掉了。
与日志墙同源——三处列表共用同一个渲染器 `logLine(e)`。

理由三条：
①**1～3 是同一个渲染器 `logLine`**，改它一处即三处齐修——只修短信记录反而要给渲染器加旗标传参，**diff 更大**；
②**1 号（城市日志，可跨 9.5 天）比报案的 2 号（5 天）更严重**，修 2 而留 1 说不过去；
③4、5 是同一个缺陷的另外两处自渲染副本，各一行，留着就是给后来人埋坑。
**没有超出「时间戳」这一个主题**：未动列表容量、未动排序、未动样式、未动额度机制、未动短信生成、SIM 零改动。

## 10.3 治法

在 PURE 块新增**唯一格式函数** `PURE.fmtStamp(t)`：

```
fmtStamp(t){ return 'D'+PURE.dayOf(t)+' '+PURE.fmtTime(t); }      // → "D75 04:40"
```

格式**对标既有先例**（宪法第 1 条）：顶栏早就写「D75 周四」，存档行早就写「已存 · D75 12:30」
——玩家已经认这套 D 号词汇，不引入界面上不存在的新名词（宪法第 9 条）。
五个渲染点全部改走它；存档行由原先手拼的 `'D'+dayOf+' '+fmtTime` 并入同一函数，**输出逐字不变**。

取「每条都打日期戳」而非「跨日处插分隔条」的理由：分隔条是**有状态**的
（要记住上一条是哪天），而三个列表都会**从头部裁剪**（400/120/14 条上限）、
还会被 `patchLid` 按 lid 原地替换、页面重载后重新灌入——
任一环节都可能把分隔条裁掉或错位，留下一段无标注的条目。
逐条打戳是**无状态**的：只依赖该条目自身的 `t`，裁剪、替换、重载、乱序一律不影响。

# 第十一章 · 追加二：语气词闸漏了「哈」

## 11.1 病症与病根

决策者实测（v29 线上，沈小满两条回信）：

```
哈？买房？…你谁啊，老给我发短信，是认识我吗？还是发错了？
哈，这话说得跟我妈似的…你谁啊，老发这种没头没尾的，别是发错人了吧？
```

病根**不用推测，第 18 单自己写在代码注释里**：

```
// 可调：语气词起手表。条目可为一字或两字——「哈」单字会误伤哈尔滨/哈欠/哈密瓜一类实词，
// 故只收「哈哈」；其余各字词首除语气词外无常用实词，单字即可判。
const LEAD_INTERJ=['欸','诶','哎','唉','呀','哟','嘿','嗨','咦','哦','噢','喔','嗯','啊','呃','哈哈'];
```

沈小满钻的正是这个当时明知而留下的缝：单个「哈」不在表里，「哈哈」才在。

## 11.2 治法：把判据从「哪个字」推进到「字后面跟什么」

**不改回禁词表**（第 13 单与 v28 已两次实证禁词表可换词绕过），判据仍然只看结构。
新增一张**歧义单字表**，与主表分开：

```
const LEAD_INTERJ=[…16 条…,'哈喽'];        // 无歧义者：单字/多字直判
const LEAD_INTERJ_AMB=['哈'];               // 歧义单字：既是语气词，又能作实词词首
const LEAD_STOP=/[\s，。！？、；：,.!?;:~～…—－\-"'“”‘’「」『』（）()【】\[\]]/;
```

判据一句话：**看「哈」后面跟的是什么，不看后面接的是哪个词**。

- 「哈」后紧跟**标点、空白、或到句末**（`charAt` 越界返回空串）→ 语气词，**拦**
- 「哈」后紧跟**汉字** → 实词（哈尔滨／哈欠／哈密瓜），**放行**

这与第 13 单的教训一致：拦的是**结构**（拿语气词起手），不是**内容**（说了哪个短语）。
模型换成「哈！」「哈。」「哈 」照样拦；模型真要写哈尔滨也不会被冤枉。

顺带补两处：
- 主表加 **「哈喽」**——它是两字问候语（哈＋汉字），在新判据下会被当实词放行，
  故按「哈哈」的先例以整词入主表。属同一条缝的另一半，不是新增禁词。
- `redoLead` 重生成指令的举例里加上「哈」（原为「欸／诶／哎／呀／哟／嘿 这类」）。

**「其余候选字是否存在同类缝隙」的排查结果**：
逐条通查主表 16 条既有条目——欸／诶／哎／唉／呀／哟／嘿／嗨／咦／哦／噢／喔／嗯／啊／呃／哈哈，
各字作词首时除语气词外**无常用实词**（不构成「哈尔滨」式冲突），故**无同类缝隙需补**，
歧义表现仅「哈」一条。门禁另加两条断言锁死两表**零重叠**——
歧义字一旦同时留在主表就会被单字直判，结构闸等于失效。

## 11.3 判据边界（明确写清，免得后来人误解）

| 情形 | 例 | 结果 | 为什么 |
|---|---|---|---|
| 哈＋标点 | `哈？买房？` | 拦 | 语气词 |
