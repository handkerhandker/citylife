## 一 · 取证六问：先出报告，再下刀

### 第 1 问　每条 AI 文案的请求是怎么发出去的？

**逐条独立发，fire-and-forget，不 await；落字是「谁先回来谁先贴」。** 代码路径逐处如下：

| 挂点 | 代码路径 | 发法 | 落字处（改前） |
|---|---|---|---|
| 短信内心独白 | `drainLog()` → `enhanceMessage(e)` | 逐条独立，**不 await** | 函数尾部 `patchLid(e)` |
| 同屋对白 | `drainLog()` → `enhanceChat(e)` | 逐条独立，**不 await** | 函数尾部 `patchLid(e)` |
| 睡前日记 | `loop()` → `runReflection()` | 四人**打包一车**（`batch=true`，`prio=true` 插队） | 尾部循环内逐条 `patchLid(e)` |

`drainLog()` 里那一句就是三个挂点的总闸：

```js
if(state.llm.on && e.lid>aiFloorLid && !e.llm && !e.llmPending){
  if(e.type==='player' && e.msg){ e.fb=e.thought; e.thought='（对着屏幕想了想⋯）'; enhanceMessage(e); }
  else if(e.type==='chat' && e.with){ e.fb=e.thought; e.thought='（聊得正起劲⋯）'; enhanceChat(e); }
}
```

`enhanceMessage(e)` / `enhanceChat(e)` 都是 `async` 函数且**返回值被丢弃**——发出去就不管了。

**并发上限：2。** 在 `pumpLLM()` 第一句：`if(llmActive>=2 || !llmQueue.length) return;`
队列 `llmQueue` 是 FIFO，`prio` 为真时 `unshift` 插队（日记走这条）。

**入队顺序 ≠ 回包顺序**，至少五条岔路会把顺序打乱：

1. 并发上限 2 —— 两条同时在飞，谁快谁先回。
2. 语气词闸重生成（第 18 单）要**再排一次队**，那条就慢一整轮。
3. `callClaude` 首轮拿到 `null` 会 `await sleep(800)` **再排一轮**。
4. 直连失败转中转：两级死线不同（`direct:4000` vs `relay:15000`），走中转的天然慢 11 秒起。
5. 日记 `prio=true` 插队，把已在排的对白往后挤。

**结论：病症一（时间倒流）坐实，根因就是「各挂点自己在函数尾部 patchLid」。**

### 第 2 问　请求失败时各走哪条分支？**有没有哪一条会让占位符永远留在墙上？**

#### 有。而且不止一条。逐条列出：

| 失败形态 | 走哪条分支 | 改前会不会永挂 |
|---|---|---|
| 网络错 / 被拦截 | `rawCallClaude` 的 `catch(err)` → `hardFail=true` → 转中转 → 仍失败则 `j=null` | 否（回落 `e.fb`） |
| 超时 | `fetchWithDeadline` 的 `Promise.race` 让 timeout 赢 → `catch` → `j=null` | 否 |
| HTTP 非 200 | `if(!r.ok){ L.lastErr='HTTP '+r.status; }`，`text` 取空 → `parseJsonLoose` 返回 null | 否 |
| JSON 解析失败 | `parseJsonLoose` 返回 null → `j=null` | 否 |
| relay 报错 | `rawCallRelay` 的 `data.error` 分支 → `j=null` | 否 |
| **promise 永不 settle** | `job.tid` 的 `jobLimit` 死线兜住 → `settleJob(job,null)` | 否，但**极慢**（见第 3 问） |
| **函数体内任何一处抛异常** | **无人接** | **是 —— 永挂** |
| **会话中途产生的孤儿** | **无人管** | **是 —— 永挂** |

#### 第 26 单的 `settleOrphanLLM` 管不管会话中途的孤儿？**明确结论：不管。**

任务书点名要查的就是这条，结论是**会话中途出错的孤儿没有任何人管**。三条证据，可复跑：

**证据 A　三个挂点都没有 `try/finally` 罩住 `llmPending`（改前实测）**

```
enhanceMessage   置在途:有  清在途:有  try/finally 罩住:**无**
enhanceChat      置在途:有  清在途:有  try/finally 罩住:**无**
runReflection    置在途:无  清在途:有  try/finally 罩住:**无**
```

`e.llmPending=false` 与 `patchLid(e)` 都写在函数体尾部的**正常路径**上。函数体内任何一处抛异常
（`patchLid` 的 `document.querySelector` 遇到畸形 `lid`、`noteUtter`、`pushLog`、以及
fire-and-forget 的 async 函数无人 `catch` 的 rejection），这条就**永远停在 `llmPending=true`**。

**证据 B　`settleOrphanLLM` 全站只有一个调用点，且在开机分支里**

```
第 1646 行：function settleOrphanLLM(w){          ← 定义
第 1660 行：if(bootWorld) settleOrphanLLM(state.world);   ← 唯一调用点
⇒ 调用点共 1 处，且在 if(bootWorld) 开机分支内。
```

它只管**开机那一刻**读到的存档里的在途条目（第 26 单治的「关页时在途」），
**会话中途卡住的，它一次都碰不到**。

**证据 C　卡住之后还有没有机会被重新点着？没有。双重永挂。**

- `drainLog` 的 AI 闸是 `!e.llmPending` —— 卡在 `true` 就**永远进不来**。
- `drainLog` 的游标 `state.logSeenLid` **只增不减** —— 已上过墙的条目**不会被第二次遍历到**。

两道一起：等不到回包，等不到重试，也等不到清道夫。

### 第 3 问　`AI_TIMEOUT` 现值是多少？盖不盖得住所有失败形态？

**现值**（`city-life-framework.html`，未改）：

```js
const AI_TIMEOUT={direct:4000, relay:15000, batch:30000};   // 毫秒
function jobLimit(batch){ return 2*(batch?AI_TIMEOUT.batch:AI_TIMEOUT.relay); }
```

**盖不住。** 分两类说：

**其一：盖得住但慢得离谱。** 单条对白的协议上界，逐段累加：

```
queueCall 第一轮   jobLimit(false) = 2×15000 = 30000ms
callClaude 重试前  sleep              =      800ms
queueCall 第二轮   jobLimit(false)    =    30000ms
                                     ──────────────
                                        60800ms
```

**关键换算**：主循环里写着 `state.simAcc += dtFrame*10*w.speed;　// 1 真秒 = 10 模拟分钟 × 速度`。
故 1× 速度下 **1 游戏小时 ＝ 6 真秒**，60800ms ＝ **10.1 游戏小时**。

> 决策者实测「D110 19:50 与 20:10 两条到 D111 06:40 仍挂着」＝ 10 小时 50 分游戏时间。
> **与协议上界 10.1 游戏小时正好同量级。** 若再叠上语气词闸的重生成一轮，上界翻倍到
> 121.6 秒 ＝ **20.3 游戏小时**；日记（batch，`jobLimit=60000`）更是到 **40 游戏小时**。
> 所以病症二**不必假设「请求真的死了」也能完整解释**——协议自己就允许挂这么久，
> 而且没有任何人按游戏时间去量过这个数。这是第 2 问之外的第二条独立根因。

**其二：真的盖不住，「既不成功也不超时、就那么挂着」的路径有两条：**

1. **函数体抛异常后没走 finally**（第 2 问证据 A）——`AI_TIMEOUT` 与 `jobLimit` 都在 `callClaude`
   *内部*，异常发生在它*外部*（回包之后的赋值/副作用段），死线根本管不着。
2. **页面切到后台，`setTimeout` 被节流。** `job.tid` 与 `fetchWithDeadline` 的 `tid` 都是
   `setTimeout`。浏览器对后台标签页把定时器节流到秒级、隐藏 5 分钟后进一步降到分钟级，
   死线本身就晚点了。**这条直接决定了本单的死线不能再用 `setTimeout` 去判**（见第三章）。

### 第 4 问　实测复现（三种情形，改前 / 改后对照）

## 三 · 治法：落字排队（pen）

新增一段 **`pen`（落字排队）** 机器，整块在 DOM 层，**一次 `w.rng()` 都不掷、一次 AI 都不调**。

```js
const PEN_TTL_MS=20000;   // 可调：占位符收尾死线（真实毫秒）
const penReg=[];          // 待落字登记表，按 (e.t, e.lid) 升序；会话级，不入存档
```

四个函数，各管一件事：

| 函数 | 职责 |
|---|---|
| `penAdd(e, fbAfter)` | 占位符挂上墙的**同时**登记，按 `(e.t, e.lid)` 插到有序位；`fbAfter`＝死线兜底时该补的副作用 |
| `penReady(e, text, llm, after)` | 回包到了。**返回 `false` ＝ 这条早已落定，整包丢弃** |
| `penFlush()` | **只从队头连续放行**——「前一条没落字，后面的按住不贴」就是这个 `while` 的循环条件 |
| `penSweep(nowMs)` | 死线扫描，主循环每帧调；登记表为空即刻返回 |

### 三条设计裁决，逐条说理由

**① 死线在主循环里按真实时钟判，不用 `setTimeout`。**

```js
  drainLog();
  penSweep(now);   // 紧跟 drainLog
```

理由：第 3 问查出来的第二条无底路径就是**后台标签页把 `setTimeout` 节流到分钟级**——
拿 `setTimeout` 去判死线，等于用一把会被冻住的尺去量「有没有挂太久」。
放在 `loop()` 里则：页面隐藏时 `loop` 不跑，但墙也没人看，且 `drainLog` 同在 `loop` 里，
不会有新条目挤进来；**一旦回到前台，第一帧就把所有过期的收干净**。
另外 `loop()` 不受 `w.speed` 影响（只有 SIM 步进受），故**世界被按停时占位符一样会收尾**。

**② 死线取值 `PEN_TTL_MS = 20000`，理由如下。**

- **下边界**由健康请求定：单轮健康上界＝中转线路死线 `relay:15000ms`（直连 `4000ms` 更短，
  工件内走直连）。留约 33% 排队余量 → **20000ms**。再往下压会连中转线路的正常回包一起砍掉，
  墙上就几乎全是模板字了。
- **上边界**由病症定：它必须明显小于协议上界 60800ms，否则等于没治。
- 20000ms 恰好卡在**「一轮打得完、两轮打不完」**之间：健康请求照常落 AI 文案；
  病态请求在 20 秒（1× 速度下 **3.3 游戏小时**）内被兜底句落定。
- 常量集中在一处，改一个数就是改全站行为。

**③ 兜底取字只认 `e.fb`，绝不现抽。**

第 27 单的原话：抽字要掷骰子，而 AI 回包的时刻由网络说了算——若等失败时再抽，
rng 流的位移就跟着网络快慢走，**同一份存档两次跑出两个世界**。
死线到点同样是「网络说了算的时刻」，故 `penSweep` 里写死 `it.text=it.e.fb||null`，
**整块 pen 一次骰子都不掷**。这就是世界指纹逐字节不变的结构保证（已立断言）。

### 三个挂点的改动形状（三处同形）

```js
async function enhanceChat(e){
  e.llmPending=true;
  penAdd(e);                      // ← 登记排在一切可能抛异常的语句之前
  ...
  try{
    ... j=await callClaude(chatPrompt); ...
  }catch(_){ j=null; }            // ← 报错也得落字
  finally{
    penReady(e, txt, good, ()=>{ /* 副作用只在本次落字真的赢了时才跑 */ });
  }
}
```

- **`penAdd` 排在一切可能抛异常的语句之前**——登记不上就没人给它收尾，那正是改前的永挂形态。
- **`try/catch/finally` 罩住整段**——第 2 问查出的「函数体抛异常」这条路，从此也归 `finally` 收。
- **副作用（短信回信 / 已读不回 / 两人的「记在心里」）挪进 `penReady` 的 `after` 回调**，
  只在本次落字真的赢了时才跑。迟到的回包被拒，副作用也一并不跑——
  否则会出现「内心独白是兜底句、回信却是 AI 写的」这种自相矛盾的一屏。
- 「记在心里」那条的时刻仍取**回包这一刻**（`const t=w.t` 提到闭包外），与改前逐字同源。

### 收尾覆盖表：第 2、3 问查出的每一条路径都有对应收尾

| 失败形态 | 谁收的尾 |
|---|---|
| 超时 | `callClaude` 返回 null → `finally` → `penReady(e, e.fb, false)` |
| 报错 / 被拦截 / 断网 | 同上 |
| HTTP 非 200 | 同上 |
| JSON 解析失败 | 同上 |
| relay 报错 | 同上 |
| **promise 永不 settle** | `penSweep` 死线（20000ms），**不再依赖 `jobLimit` 的 60800ms** |
| **函数体抛异常** | **新增的 `try/catch/finally`**（改前无人接） |
| **页面切走后回来** | `penSweep` 在 `loop()` 里，回到前台第一帧全部收掉 |
| **关页时在途**（第 26 单已治） | `settleOrphanLLM`，开机时收，**未动** |
| 迟到回包（兜底已落定） | `penReady` 返回 `false`，整包丢弃 |

## 八 · 留给决策者的两个读数

1. **代价的量化**：情形一里，20:10 那条 3000ms 就回来了，被按到 3500ms 才上墙——**滞后 500ms**。
   这就是「按序落字让墙略滞后」的实测值。滞后上界＝`PEN_TTL_MS`＝20 秒（1× 下 3.3 游戏小时）。
2. **收益的量化**：占位符最长存活 **60800ms → 20000ms**，1× 速度下 **10.1 → 3.3 游戏小时**，
   降幅 67%；且「函数体抛异常」与「会话中途孤儿」这两条**原本无底**的路径，从此都有了收尾。

若决策者认为 3.3 游戏小时仍偏长，`PEN_TTL_MS` 是单点可调常量——
但下调到 15000ms 以下会开始砍掉中转线路的正常回包，那是取值的下边界，请一并裁定。
