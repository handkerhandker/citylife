# 关系状态机 · 三期方案 B 档 v1（**关系进行为**：老友会主动登门）

> 一句话：A 档（第 88／91／96 单，v83–v89）只让关系**被记下来、被看见**；B 档让关系**改变行为**——
> 本方案只提两件小事，且**推荐先做第一件**：
> ① **登门**：关系两边都到「老友」的人，会在自己空闲、对方在别的屋子且没上班时**走过去**找他
> （一天至多一次；**死分钟数＋null 独白 ⇒ 一步 rng 都不摇**，照第 95 单"去找寿星"那支先例）；
> ② **凑一起**（后做）：同屋聊天那一次掷骰的概率按关系档位乘一个系数（0.35 → ×1.0／1.15／1.3／1.45，
> 上限 0.95）——**只改比较阈值、不改抽签次数**（照第 49 单先例，rng 流不位移）。
> C 档（关系进目标谓词与节日联动）**不在本方案**，等 B 档落地后另说。

## 一 · 为什么现在提

第 68 单的方案把关系切成 A／B／C 三档，A 档当时就做掉了（第 88 单）。
此后第 91／96 单给了两场"交心"戏、第 93–95 单把礼物这条线接通——**关系已经会"改变会发生什么"**，
但它**仍然不改变任何取舍**（`decide()` 一个字没读它）。B 档就是那"下一步"：
让对方**怎么对待你**变成看得见的事。

## 二 · 出处（本单复核）

| 出处 | 逐字摘 | 抄什么 |
|---|---|---|
| Nookipedia·Villager（https://nookipedia.com/wiki/Villager，**2026-10-03 实测 HTTP 200**） | 「When **visiting a house**, villagers can be seen exercising, cleaning, or singing. The player can also **invite villagers to the designed house**.」 | **串门是日常行为**（"去谁家里"这件事在同类作品里就是一行行为） |
| 星露谷 wiki·Friendship（2026-10-03 实测 HTTP 200，沿用） | 「As friendships deepen, the villagers' dialogue lines become more friendly…」 | 关系深浅要改变**对方怎么对待你** |
| Nookipedia·Friendship（2026-10-03 实测 HTTP 200，沿用） | 「**+1 point — speaking to the villager for the first time each day**」 | 关系是按天累积的——所以"熟了会主动来"要落在**天**这一档上 |

**不抄**：拜访时的"参观动画/家具展示"（本作没有可交互家具）；也不抄"关系高就送你东西"那套（礼物线已独立成单）。

## 三 · 设计（两件，各可独立落地）

### ① 登门（**推荐先做这一件**）

```js
// decide() 空闲段里加一支（排在平常闲聊之前、社交之后）：
const 老友线=REL_TIERS[3].lo;                                            // 35＝「老友」（**同一张档位表**，不另立门槛）
const 老友=w.agents.find(o=>{
  if(o===ag) return false;
  if(relGet(ag,o.id)<老友线 || relGet(o,ag.id)<老友线) return false;      // 两边都到「老友」
  if(roomOf(o.anchor)===roomOf(ag.anchor)) return false;                 // 已经在同一间屋 ⇒ 不必"去"
  if(o.activity && o.activity.type==='work') return false;               // 人家在上班 ⇒ 不去打扰
  if(ag.visitDay===PURE.dayOf(w.t)) return false;                        // 一天至多一次
  return true;
});
if(老友){
  ag.visitDay=PURE.dayOf(w.t);
  setActivity(w,ag,老友.anchor,'stroll','去找'+老友.name,20,null,'去找'+老友.name);   // 死分钟数＋null ⇒ 零 rng
  return;
}
```

| 要件 | 落成 | 为什么 |
|---|---|---|
| **只在两边都到「老友」** | 读 `REL_TIERS[3].lo`（**同一张档位表**，不另立门槛） | 关系是半张表（第 88 单口径），"去串门"要两个人都认 |
| **不摇 rng** | 死分钟数 20 ＋ `null` 独白（照第 95 单） | 只改"去不去"，不改"摇不摇"——世界指纹与 rng 流都稳 |
| **一天至多一次** | `ag.visitDay` 一个数字（照 `noteDay`／`missWeek` 先例） | 不刷存在感；也给"他今天已经来过"一个可读的账 |
| **不打扰上班的人** | `o.activity.type==='work'` 就跳过 | 与第 88 单"上班／吃饭／睡觉一概不碰"同一条红线 |
| **只占空闲那一档** | 排在上班／吃饭／小憩之后 | 同上 |
| **到了之后** | 什么都不用做——下一拍两人同屋，平常那套（闲聊／交心／礼物）自然发生 | 不给它专门的戏（省得又长出一条平行机制） |

## 四 · 风险与代价（照实登记）

| 项 | ① 登门 | ② 凑一起 |
|---|---|---|
| 新增世界状态 | `ag.visitDay` 一个数字（照 `noteDay`） | 无 |
| 摇不摇 rng | **不摇**（死分钟数＋null） | 不摇（只换阈值），但**阈值变了 ⇒ 行为变** |
| 世界指纹 | 可能变（他站的位置变了 ⇒ `anchor` 在指纹口径里） | **必变** |
| sim30 六项 | 要复测（30 天窗口内会走到"老友"吗？——实测**不会**：30 天最多到 29，故六项**应当不动**） | 要复测（一定会动） |
| 门禁里那几条读数闸 | 要全跑（尤其第 64 单"生日上卡"、第 88 单"关系涨落"、第 92 单"长跑不变量"） | 同上 + `social_burst` |
| 可逆性 | 高（删那一支即回到现状） | 中（阈值一改就动世界，回到旧值即复原） |

**红线照旧**：不夺走（不扣钱、不扣饭、不影响上班与睡觉）；不新增素材；零 AI；同种子逐字可复现。

## 五 · 验收方案（照既有先例，逐步做）

1. **跨版本逐拍比对**：`node tools/rel-audit/compare.cjs --before=HEAD`（必要时加 `--忽略=锚点`）——
   登门这一支应当只让"锚点"变，**钱／饭／班／睡与忙到几点这一列必须一字不差**；
2. **A/B 定标**（旋钮配对，照第 52／63／102 单）：把 B 档临时关掉跑同一批种子，量
   "**登门次数／同屋共处时长**"这两个读数（前者是这一档的"做了没有"，后者是它的实际效果）；
3. **反向自查**：把门槛抬到不可能（`REL_TIERS[3].lo=999`）⇒ 同一构造**一次都不登门**；
4. **六项复测**：`node sim30.js` 全绿 + `node worldsig.js` 记账（变了就逐条写清变了什么）；
5. **自测四件**：门禁九步全绿 → 冒烟档 1 → 全按钮扫描（双档）→ **30 分钟浸泡**（行为改动这一档必须跑满）；
6. **交付件**写清：改了哪几处、指纹三个数各是多少、A/B 读数、以及"哪些"没动（照第 90／95 单的体例）。

## 六 · 我的推荐与排期

**先做 ① 登门**：它是"零 rng、最可逆、最像日子"的那一件，且**落在 30 天窗口之外**（第 88 单的探针实测：
关系要 D36–D41 才到老友）⇒ 六项与两枚指纹**大概率不动**，风险最低。
**② 凑一起**等 ① 落地、且有人点头之后再动（它会改 30 天窗口内的行为，属"动世界"那一档）。

> 本文件是**方案**。按母法「改动分级」，① 只需**新增一个数字字段 ＋ 一支零 rng 的分支**（照 `noteDay`／第 95 单先例），
> 与"新增世界状态／换方案"不同级；② 会改 30 天窗口内行为，按分级**要先点头**。

## 七 · 明确不做

- 不做"关系低就冷脸/拒绝"（本作是"看人过日子"，不是养成对错）。
- 不做"关系高就能指挥对方做事"（那是 B 档之外的玩法，会破坏"各有各的日子"）。
- 不做关系数值的交易化（呼应母法：收费只卖支持不卖强度）。
